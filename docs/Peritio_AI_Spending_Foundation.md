# AI spending foundation — Batch 9F.2B

This is an opt-in recording foundation, not approved customer spending policy.
An independent Claude Opus audit is required before migration or staging deployment.
No deployment, shared migration, final numeric limit, mobile change or strict speech
grant is part of this batch.

## Flags and startup

- `AI_SPEND_LEDGER_MODE=off` (default): existing budget path, defaults, enterprise
  exemptions, provider errors and usage-event behavior are unchanged. No ledger
  tables or new secret are required or queried.
- `AI_SPEND_LEDGER_MODE=record`: PostgreSQL, explicit `PERITIO_ENV`, and a distinct
  `AI_SPEND_LEDGER_HMAC_SECRET` of at least 32 characters are mandatory. All API
  instances must use the same secret. Do not rotate it across overlapping instances
  without draining in-flight/idempotency operations first.
- Any other mode, including `enforce`, fails configuration validation. There are
  no runtime user/org/concurrency policy knobs in this foundation. Store rules and
  concurrency bounds are internal primitives exercised in integration tests only.
- Record-mode startup/readiness checks 025 and existing `ai_usage_events` columns before
  serving. Missing migration, credentials or permissions fail closed; neither
  startup nor request handling runs 025 or falls back to unaccounted dispatch.

Existing `OPENAI_MAX_DAILY_*` settings remain in effect in both modes. Source
defaults are not evidence of the actual Render settings. Do not increase caps or
change `FOCUS_TOPIC_AUTHORITY` as part of enabling recording.

## Schema and permissions

Apply `api/sql/025_ai_spend_ledger.sql` explicitly using the migration owner after
audit. Migration 024 is unchanged. The existing usage store/schema must already
exist. 025 creates only three new tables and indexes, with no data backfill:

- `ai_provider_attempts`: stable UUID, environment, authorized actor/org, optional
  server-validated session identity, operation/model/policy, opaque idempotency key,
  keyed request fingerprint, dispatch/outcome timestamps, lease, nullable usage
  measurements, allowlisted failure metadata, optional provider request ID and
  one unique existing usage-event identity.
- `ai_limit_buckets`: UTC day, fifteen-minute or minute windows keyed by environment,
  scope/person/org, metric and window; nonnegative reserved/consumed units.
- `ai_attempt_claims`: foreign keys to attempt/bucket, original reservation and
  nullable settled amount. UUIDs are generated by the application: no extension or
  sequence permission is required.

Runtime role requires schema USAGE plus SELECT/INSERT/UPDATE/DELETE on the three
tables and its existing `ai_usage_events` permissions. Migration owner requires
CREATE on the intended schema. API startup never needs permission to create 025.
The usage-event association intentionally is not a foreign key: existing account
deletion/deidentification may remove an event without silently canceling a billable
claim. No name/email, prompt, transcript, raw audio, response body or credential
is stored as request material. The actor/org identifiers remain operational metadata.

## Atomicity, dispatch and reconciliation

The ledger shares the existing global AI-budget PostgreSQL advisory lock and
reservation helper. One transaction checks the original daily limits, inserts the
original usage event, records the attempt, and claims sorted scope/window/metric
buckets. A rejection rolls everything back. There is no second sum of old and new
records for reporting: existing reports still count `ai_usage_events` once.

Transactions acquire global lock, then attempt and sorted buckets. Provider work
starts only after reservation and dispatch transactions commit. No transaction is
held across network/AI/extraction work. Conditional bucket updates and active-lease
indexes support the future internal limits across independent processes. Existing
global budget serialization remains; this does not redesign reporting or app_state.

- Same actor/environment/idempotency key with the same canonical HMAC returns the
  existing attempt, never another claim. Different org, session, model or request
  material conflicts. Dispatch is one-time; a repeat does not authorize another call.
- Successful settlement atomically finalizes claims and updates the same usage
  event. Duplicate identical settlement is a no-op; conflicting terminal settlement
  is rejected. Post-response event enrichment preserves the original event date
  in record mode, so midnight cannot move the charge into the next day.
- Pre-dispatch failure releases spending claims and removes the unused usage event;
  its request count remains. Dispatch-response loss is uncertain, not proof of no work.
- Provider exceptions after dispatch retain the conservative reservation as `unknown`,
  even for errors that might ultimately be nonbillable. This is deliberately more
  conservative than the off-mode release-on-exception behavior. No automatic refund
  is based merely on timeout/abort/status wording.
- Unknown can reconcile to measured success or definitively measured failure.
  Unmeasured dimensions retain their conservative amount rather than becoming zero.
  Settlement failure rolls back both structures; retries are idempotent. After a
  successful provider result, settlement errors are logged with safe categories;
  the caller receives the actual result and the reservation is retained. No response
  is fabricated and no automatic provider retry is introduced.
- Execution leases are 120 seconds for the currently <=45-second provider calls.
  On new reservations, a bounded sweep reconciles expired leases; the reusable
  `reconcileExpired()` operation can also be run independently. Expired reserved
  attempts release unspent claims. Expired dispatched attempts become unknown and
  keep their usage. Unknown attempts retain their execution slot until the original
  lease expires, since abort is not proof of remote cancellation. Expired leases
  never count as active concurrency indefinitely.
  A lease does not prove that OpenAI stopped work or that a retry is free.

The execution adapter currently creates a fresh opaque key per provider invocation.
The `requests` metric counts accepted provider-operation attempts, including those
that fail before dispatch; it is not yet a counter for every HTTP request. Durable
HTTP throttling before expensive preparation remains next-batch work.
The store supports cross-process idempotency, but this batch does NOT introduce
HTTP idempotency contracts, scoring single-flight, durable response caching or
cross-process speech-result reuse. These need explicit integration in the next batch.
Optional session attribution is supported by the store; raw client session claims
must not be passed as registered identity. Current invocation recording leaves it
null until the authoritative session binding is carried through the adapter.

## Path adoption and measurement

Record mode covers all existing `invokeAiProviderWithBudget` paths: opening, turn,
scoring, transcription, direct/background-prefetch TTS, platform-admin custom scenario
generation and customer Practice Scenario generation. No client contract changes.

Text completion usage uses provider token totals, including provider-reported
reasoning usage. TTS characters are measured from normalized submitted text. STT
duration and audio-token usage are NOT measured by the existing provider adapters;
byte count is not audio duration. Estimated cost and STT duration stay NULL/unclaimed
in current recording; no dollar/audio ceiling can be claimed yet. The engine supports
validated duration/estimated-cost units, but does not accept those from HTTP clients.
Provider IDs can be persisted when supplied by a trusted adapter; current adapters
do not return them. Unknown outcomes are inspectable in the ledger; existing reports
still include their conservative usage reservation and do not imply confirmed billing.

No change to simulation-minute allowances, monthly entitlements, enterprise
exemptions, deadlines, completion grace, scoring schema or models. Current TTS remains
unbound to sessions/messages, and existing process-local rate limiting remains.

## Controlled deployment order (do not execute in this batch)

1. Audit the local commit. Verify Render auto-deploy, actual instance topology,
   active revisions, DB roles and actual budget settings; do not infer them from docs.
2. Keep the new gate off. Back up and apply 025 with the migration owner, then verify
   schema/indexes and runtime grants read-only. This must not alter existing data.
3. Deploy the audited code with gate off; verify normal health and old budget tests.
4. Confirm all provider-spending processes use the audited revision; configure the
   same fingerprint secret/environment and enable record mode in a coordinated restart.
5. Verify success, rejection, unknown-outcome and midnight accounting with authorized
   staging smoke tests. Observe row/write volume and reconcile unresolved attempts.
6. Do not activate later limits during a mixed-version rollout. Older APIs still
   honor old global limits but do not participate in new org claims. Drain/remove
   old instances and external spending writers, verify revision/config on every
   instance, and gate new admission before activating reviewed enforcement. If this
   cannot be established, a controlled maintenance cutover is required; ordinary
   rolling deployment is insufficient.

New buckets do not backfill historical usage. Activate future daily ceilings only
after a complete UTC accounting window with all spenders participating, or after a
separately reviewed conservative opening-balance procedure. Do not ignore earlier
same-day old-version spending when enabling a ceiling midway through a day.

Rollback: disable recording without dropping new tables or removing conservative
usage events/claims. Reconcile unknowns explicitly. Returning to old code does not
enforce future organization ceilings; do not use that rollback after enforcement
activation without disabling admission. Never roll back by deleting budget history.

## Overhead, retention and remaining approval

Reservations use one short transaction and indexed rows, normally 9 claims/buckets
(requests/calls/text tokens across three scopes), or 12 with TTS characters. Each
bucket uses one conditional UPSERT, plus one claim insert; settlement updates only
that attempt's claims and buckets plus its existing event. Dispatch adds one short
update transaction. Record mode adds a separate connection pool bounded by
`PG_POOL_MAX`; account for this across instances when sizing PostgreSQL connections.
No monolithic app_state write is added.

No automatic metadata purge is activated. Proposed retention is 90 days for fully
settled attempts/claims; delete claims before attempts and delete only unreferenced
expired buckets. Never expire unknown claims just to reclaim capacity. Existing
usage-event retention and privacy operations remain unchanged. Before activation,
approve metadata retention/deidentification, unknown reconciliation ownership,
backup/restore consistency and a safe cleanup job. Runtime requires no new reporting UI.

Next batch: approve actual per-user/org/platform policy; validate audio duration and
cost estimates; wire durable request throttling, session/scoring idempotency and
completion capacity reservation; preserve approved allowances and recovery. Strict
TTS grants remain a separate coordinated mobile rollout. Do not raise global limits
as a substitute for this work.
